# Sky TTLR — Custom Code

Sky is rebuilding its TTL (Time To Learn) product in Webflow. Webflow's own Designer can't express the interactive, stateful pieces the rebuild needs — paging through episodes without a full page load, a drag-and-drop quiz, per-member progress that survives across sessions — so those pieces are written as vanilla JS/CSS and dropped into Webflow's Custom Code embeds. This repo is where that custom code lives and is documented. Prepared by MakeBuild.

Each file is self-contained and documented inline (top comment block) with exactly what it targets, what it needs from Designer, and what it doesn't solve yet. This README explains what the project does as a whole; check the file itself for full implementation detail before wiring anything up.

## What each component does

All components below live in `sky-ttlr.js`/`sky-ttlr.css`, each under its own clearly-commented section — nothing here is a separate file anymore (see Install).

**Episode router** turns a CMS list of episodes into a single-episode viewer. All episodes in a Series render into the page as normal (that's how Webflow's CMS binding works), but the script hides every item except one and toggles `.ttlr_episode_button.is-prev` / `.is-next` to step through them — no page navigation, no reload, and a brief opacity fade between episodes (`.ttlr-episode-fade` in `sky-ttlr.css`, 150ms, kept in sync with `EPISODE_TRANSITION_MS` in the JS). It's sequential (fade out fully, then fade in), not a simultaneous crossfade — having both episodes in normal document flow at once (even briefly) visibly jumps the page layout, which is layout-dependent and doesn't need to be for this to look right. The current episode number is mirrored into a `?episode=` query param via `history.pushState`, so a link straight to `?episode=3` opens on that episode. Clicking Next marks the episode you're leaving complete (clicking Prev never does — going back to re-watch doesn't count as finishing it); once every episode in the series is marked complete, it also marks series-level completion, which is what a completion badge elsewhere on the site would read. On the *last* episode, Next relabels itself "Finish Series" — clicking it marks that final episode complete (the only point this was previously falling through uncompleted), **hides the whole `.ttlr_episode_cards_section`, the episode progress bar** (`.ttlr_episode_progress_inner` + `.ttlr_episode_progress_p`), **and the bookmark button** (`[bookmark="btn"]`, not actionable on a finished episode) so the success screen truly fills the whole screen instead of just the space the episode item occupied, reveals `.ttlr_series-end_success` **and** `.ttlr_completed_episode_wrap` (both hidden by default, `.is-active` on either), fires a confetti burst, and starts a 30-second countdown written into `[data-series-element="seconds"]` (a fresh `setInterval` each time, guarded against overlapping if the screen somehow shows twice) — when it reaches 0, it auto-clicks every `[data-series-nav="next-btn"]` on the page (a no-op if there's no next series, since a disabled next button never gets a click handler attached in the first place), instead of advancing anywhere. Completion is **local-first**: `localStorage` updates and the UI repaints instantly on click, and the Memberstack write happens afterward, debounced 500ms in the background (same pattern as the site's existing stacked-apps launcher) — see Local-first storage below.

**Progress bar** is a single global (not per-episode) fill + "X / Y" readout for the whole series — it shows *where you currently are* (`currentIndex + 1` of the total), not how many episodes are marked complete. It repaints on every `show(index)` call (i.e. every Prev/Next/deep-link navigation), independent of `ttl-progress` completion data entirely. `current / total` is applied to `.ttlr_progress_fill` as a `clip-path` (revealing more of Designer's own gradient, left to right — the gradient's `background` itself is never touched by the script), with a slightly-eased transition and a brief brightness pulse (`.is-updated`, `filter` only — still never touches `background`) when moving to a later episode (never on Prev, since percent only pulses on a genuine increase). The pill-segment look is a `mask-image` computed in JS from each `.ttlr_progress_segment`'s actual rendered position, so segment count doesn't need to match episode count and Designer's own layout for the segments (flex, grid, gaps, whatever) doesn't need to match any assumption in the CSS. Segments have a `#D9D9D9` empty-state background in `sky-ttlr.css`, safe to set directly since the fill is a positioned element that always paints above them regardless of DOM order.

**Drag & drop quiz** is a matching quiz built on interact.js: each "prop" is draggable, and it only actually leaves the tray and gets placed in the DOM when it's dropped on its correct, still-empty zone (`data-correct-zone` on the prop must match `data-zone-id` on the zone) — every other drop just snaps back to the tray with a reject flash, so there's no fail state and unlimited retries. A correctly-placed prop scales to fill its zone's box and centers itself in it (CSS, keyed off `.is-correct` once the prop is a real child of the zone). It also ships a full keyboard path (Tab to a prop, Enter to grab it, Tab to a zone, Enter to attempt the drop, Escape to cancel) and an `aria-live` region that announces placements and rejections, so it doesn't depend on drag gestures to be usable. Once every prop is correctly placed it fires a `ttlr:quizCompleted` custom event that other code can listen for.

**Hero CTA button** (`.ttlr_hero .ttlr_hero_heading-wrap .secondary-button-link`) shows "Let's get started" linking to the first series in the hero carousel if nothing's been started yet, or "Resume: SN EP{completedCount+1}" linking straight to that next episode (`?episode=` query param, same as the router already reads) if some series has partial progress. If more than one series has partial progress, resumes whichever comes first in the carousel's own order — there's no reliable "most recently watched" timestamp in the current `ttl-progress` data to break ties by. Falls back to "Let's get started" if every series is either untouched or fully completed. Reads `ttl-progress` directly (local-first + Memberstack hydrate), independent of the Series cards component below — the series cards on the page are only ever used here as a lookup table (href, displayed series number), scoped to `.ttlr_hero` specifically since `.ttlr_cms_series-wrapper`/`.ttlr_series_card-wrap` are reused by other sections on the same page (Re-Watch, bookmarks).

**Series cards** (home page carousel) show each series' own completion — "3/5 Completed" or just "Completed" once finished — rolled up from the same `ttl-progress` data the episode router writes. Every `markComplete()` call on a series' own episode page now also records `completedCount`/`total` (not just a `completed` boolean once it hits 100%) against that series' id, so a home page card can read `${completedCount}/${total}` directly without any extra fetch or per-series episode list of its own — just the same Custom Field, read local-first then re-rendered once Memberstack hydrates. The badge (`.ttlr_completion_tag-wrap` / `.ttlr_badge`) is hidden entirely for a series with no recorded progress yet, rather than showing Designer's static placeholder text or a misleading "0/5". `.ttlr_series_card-inner` is sized to that same percentage (`width`) as a mini fill bar — unlike the main progress bar, its gradient IS set directly in `sky-ttlr.css` (`background-image`, two stacked `linear-gradient`s) rather than left to Designer, since the element had no fill styling of its own at all.

**Prev-content expandable cards** — clicking a `.ttlr_card-wrap.is-rewatch` opens that month's episode panel (`.ttlr_prev-episodes_wrap`), accordion-style (closes whichever other month was open first). The panel is physically **relocated** in the DOM on open — moved out of its `.ttlr_cms_month-item` (a swiper-slide of the Re-Watch carousel, so it would otherwise scroll along with that slide) into a static `.ttlr_prev-content_slot` created as a sibling of the swiper root, then moved back to its exact original position on close. This is what makes the panel stay fixed in place regardless of the carousel's scroll position — a CSS-only fix isn't possible here, since anything nested inside a scrolling/transformed ancestor stays clipped or re-contained by it no matter how it's positioned (same reasoning as the outer carousel's `cssMode` note above, one level up the DOM). `sky-ttlr.css` duplicates the open/close height animation scoped to `.ttlr_prev-content_slot.is-open .ttlr_prev-episodes_wrap`, since the page's own embedded CSS animates it via `.ttlr_cms_month-item.is-open .ttlr_prev-episodes_wrap` — a selector that no longer matches once the panel has moved. If a month ships `.is-open` by default in the static markup, that's synced to the same relocated behavior on page load, not just on click.

**Prev-content month badge** — each month card's own `.ttlr_completion_tag-wrap` ships as "Completed" unconditionally in Designer's static markup; this hides it unless **every** series featured that month (the nested `.ttlr_series_card-wrap` cards inside its own `.ttlr_prev-episodes_wrap`) is fully completed. Read-only with respect to those nested cards — only their `href` is read, to derive each series id the same `/serie/<slug>` way `initSeriesCardFill` (reverted) did — nothing about them is written, so this can't interact with `initSeriesCard` or any other series-card feature.

**Series count label** (`#series-number`) shows how many series are in the CMS-bound carousel list — content data (how many Series items exist), not member progress, so it's independent of `ttl-progress`/localStorage and Swiper — it just counts `.ttlr_cms_series-item` elements actually rendered inside `.ttlr_cms_series-wrapper` and writes `"N Series"` into the label's inner text.

**Series swiper** is a Swiper.js carousel for the landing/hero page's CMS-bound series list (`.ttlr_cms_series-wrapper`), wired to Designer's own `.swiper-button-prev`/`.swiper-button-next` elements. **Swiper's own bundled CSS is loaded** (added directly in Webflow Custom Code Head, alongside the existing `swiper-bundle.min.js` — outside this repo) — it handles all of Swiper's own slide sizing/wrapper transforms/scroll behavior; `sky-ttlr.css` only neutralizes the one part Designer doesn't want, Swiper's default absolute-positioned arrow glyphs on `.swiper-button-prev`/`-next` (`position: static`, cleared size/margin, `content: none` on its `::after` glyph), so those stay Designer's own custom SVG-icon buttons in Designer's own layout. Uses a fixed `slidesPerView: 3, spaceBetween: 20` (edited directly on GitHub after the initial `slidesPerView: 'auto'` delivery) — with a fixed number, Swiper computes each slide's width itself, so `.ttlr_cms_series-item` no longer needs an explicit Designer-set width for slides to size correctly. **`.swiper-button-next`/`.swiper-button-prev` only ever control the hero carousel** (the swiper whose container is inside `.ttlr_hero_series-wrap`) — `.ttlr_cms_series-wrapper` is reused by other carousels on the page (Re-Watch, bookmarks), and each `initSeriesSwiper()` call first looks for its own local nav-button siblings; only the hero-scoped instance falls back to the shared page-wide buttons if it doesn't find its own. A non-hero carousel without its own dedicated buttons simply gets no navigation, rather than silently stealing the hero's buttons. **Every `.ttlr_cms_series-wrapper` on the page becomes its own independent Swiper instance** — including the nested per-month series list inside `.ttlr_prev-episodes_wrap` (the Re-Watch accordion panel) and the bookmarks carousel — `initSeriesSwiper`'s own `root.swiper` guard keeps each one from being double-initialized on a re-fire, but nothing scopes which wrappers get Swiper in the first place. **Every `.ttlr_cms_series-wrapper` is initialized through `initSeriesSwiperSafe`, not `initSeriesSwiper` directly** — a thin try/catch wrapper. This matters because the one-time `document.querySelectorAll(...).forEach(...)` scan is a single loop over every wrapper on the page in document order; `Array.prototype.forEach` does not continue past an uncaught exception in one callback call, so a single wrapper throwing during Swiper init used to silently abort the whole scan for every wrapper still left in the loop (confirmed 2026-09-04: this is why every nested wrapper inside `.ttlr_prev-episodes_wrap` — 8 of them, one per month, all coming after the outer Re-Watch carousel in document order — stayed permanently uninitialized, while the hero and Re-Watch-outer carousels earlier in the DOM worked fine). A `MutationObserver` on `document.body` is also kept as a fallback for genuinely asynchronously-inserted CMS content the initial scan can't see yet. **No `cssMode`, deliberately (2026-09-05, reverted):** the outer Re-Watch carousel briefly ran in `cssMode` because its transform-based drag mechanic used to break the nested per-month episode swiper's layout while it lived inside a dragged slide. That's no longer the mechanism in play — the currently-open month's nested swiper is now physically relocated out of the carousel into a static slot (see the Prev-content expandable cards entry below), so it's never a descendant of this carousel's transformed wrapper while actually visible. Running `cssMode` without Swiper's own bundled CSS loaded also meant manually replicating its scroll/overflow behavior, which caused a real regression (clipped Designer's own `.is-open`/hover card scale effect) — reverted along with loading the real stylesheet.

**Bookmarked episodes carousel** (`#bookmarks`) clones a single Designer-authored template slide (`.ttlr_cms_month-item` inside `.ttlr_cms_month-list`, kept as the clone source and never itself shown) once per bookmark, filling in a **snapshot** of that episode's data captured at the moment it was bookmarked — no live lookup against a full episode list needed, so it works on any page. Completion state is the one thing NOT snapshotted — it's read live from `ttl-progress` at render time so a badge here can never go stale relative to actual progress. Thumbnails carry over both `src` and `srcset` from the original episode's image — `srcset` alone would otherwise keep the cloned template's own responsive image set active at matching viewport widths, overriding the updated `src`. Each card's `[data-bookmark="btn"]` is marked `.is-bookmarked` (every card here IS a bookmark, so it's always shown filled — no outline/filled toggle needed like the episode page's own button); clicking it removes that bookmark from **both** `localStorage` and Memberstack (write-as-is, same as the main bookmark toggle) and re-renders the list. The whole `#bookmarks` section is hidden entirely when there are zero bookmarks, not just left showing an empty list. **Every render also makes sure the carousel is actually a Swiper, not just a static list:** if `.ttlr_cms_series-wrapper`'s own Swiper instance already exists it's just told to `.update()` (slide count changed), but if Swiper was never initialized on it at all — e.g. the page-wide 'series swiper' pass ran before any bookmarks existed to measure — `render()` initializes it itself now, instead of leaving the carousel permanently non-swiping.

**Bookmarks** is a single global button (`[bookmark="btn"]`, not one per episode) that bookmarks whichever episode is currently displayed by the episode router. Clicking it toggles that episode's id and swaps the button's SVG icon between an outline and a solid-filled version of the same path — instantly, since this is local-first like the progress bar (see below). Icon state stays in sync as you page through episodes (each one shows its own bookmarked/not state immediately) and is restored correctly on page load. The background sync to Memberstack writes the current local bookmark list **as-is**, not merged with whatever's already on the server — bookmarks, unlike progress, aren't monotonic (removal is a real, valid action), and merging with a stale remote value used to silently resurrect anything just unbookmarked.

Bookmarks are stored as **snapshot objects** (`{ id, title, month, imgSrc, imgSrcset, href }`), not bare id strings — composed from `[data-bookmark-thumbnail]`/`data-bookmark-name` on the current episode item plus `data-bookmark-month`/`data-bookmark-year`/`data-bookmark-series-number` on `<body>`, at the moment the bookmark button is clicked (see Required Designer steps below). This is what powers the Bookmarked episodes carousel above without needing a separate live lookup. Old data from before this change (a plain array of id strings) is normalized into a stub object on read, so `.id` matching keeps working — it just renders blank fields until that episode is bookmarked again.

### Local-first storage (bookmarks + progress)

Both bookmarks and progress follow the same pattern as the site's existing app-launcher (`stacked-apps`): every click updates a `localStorage` cache and repaints the UI **synchronously** — no network round-trip on the click path — and a Memberstack write is queued afterward, debounced 500ms (`SAVE_DEBOUNCE_MS`) so rapid clicks collapse into a single write instead of one per click. On load, the UI paints instantly from the local cache, then the script hydrates from Memberstack in the background and **merges additively** (a completion or bookmark recorded on either side wins — nothing is ever un-set by a merge), so state recorded on another device/session isn't lost. Local cache keys: `ttlr-progress-local`, `ttlr-bookmarks-local`.

**Notes pad's open/close toggle is NOT handled by this script** — reverted per explicit request 2026-08-27 ("that was working flawlessly, now it's shit") after a separate CSS-then-GSAP-in-`sky-ttlr.js` version was tried and found glitchy. `[open-notes="btn"]` (appears twice in the live markup — the menu bar's own open button and the pad's own close icon) is exclusively owned by a **separate jQuery + GSAP `<script>` in Webflow Custom Code**, exactly as it was before this project ever touched it — this file only ever reads `is-open` (via `isOpen()`), never sets it or attaches a click listener to that button. Do not re-add open/close handling here without being asked again.

**Notes pad** is a resizable notepad component. Its content is a single shared note stored in `localStorage`, not scoped per page — so the same text shows up and is editable everywhere this Webflow component is placed, since `localStorage` is already global per browser/domain. Dragging `.notes_drag_line` resizes `.notes_wrap` (the inner content wrapper, not `.notes_component_wrap` itself) by setting an inline width on it (assumes the pad is anchored right and the drag line is its left edge — flip the sign in `onPointerMove` if that's backwards for your layout), never below `MIN_WIDTH` in JS (528px as of this writing, matched by the CSS `min-width` backstop for `is-open="true"` — both values have been bumped directly on GitHub more than once since first written at 280px; check the actual current values in each file rather than trusting this number), and the resized width itself persists across page loads too. `[data-notes-action="copy"]` copies the note to the clipboard and flashes `.notes_copy_success` (`display: flex` while active); `[data-notes-action="delete"]` arms a `.is-confirm` state on first click and clears the note (locally and in `localStorage`) on the second — forced to a clean unarmed state on load (regardless of the Designer markup's static class) and again whenever the pad closes (a `MutationObserver` on `is-open`, reacting to whatever external script changes it — it only resets the delete-confirm state now, and deliberately does NOT touch `root`'s width, since that's fully owned by the external open/close script; it used to clear it on close, which raced against that script's GSAP tween and caused a reported "no movement" bug), so a half-armed delete never lingers into the next time it's opened. The whole component's wiring is guarded against double-registration (`data-ttlr-notes-pad-wired`) since this site's Webflow runtime can re-fire `Webflow.push` callbacks more than once per page — without that guard, delete specifically would double-fire and skip its two-click confirm.

## ⚠ This site re-fires Webflow.push callbacks more than once per page

Confirmed 2026-08-27 via a live stack trace: this site's compiled Webflow runtime (`timetolearn.schunk...js`, an app-shell/route-transition style build) calls already-registered `Webflow.push` callbacks again after the initial page load, not just once. This isn't a bug in this repo — it's a property of how this specific site is built — but it means every feature here has to tolerate being initialized more than once on the same element.

Two consequences, both addressed:
- **A throw in one feature's callback used to silently block every other feature registered after it** for that pass (an uncaught exception inside a `Webflow.push` callback prevents this site's runtime from continuing to the next queued one). This is why, for example, the series card badges and series count label could go completely dark — not because their own code was broken, but because `initSeriesSwiper` (registered earlier in the file) threw first. **Fixed:** every `Webflow.push` registration in this file now goes through a `ttlrReady(label, fn)` wrapper that catches and logs (`console.error`) instead of throwing, so one feature's failure can never cascade into another's.
- **Re-running an init function on an already-initialized element can itself throw or double up.** Confirmed for the series swiper specifically: calling `new Swiper()` again on a container that already has a live instance crashes inside Swiper's own internals. `initSeriesSwiper` now checks `root.swiper` (Swiper stores its instance there) and skips if already initialized. Other components (episode router, drag-drop quiz, notes pad, series nav, series cards, series count label) haven't shown a *crash* from double-init, but most weren't specifically audited for double-init side effects like duplicate event listeners either — if a future bug looks like "an action fires twice" (a click handler running twice, a debounced save firing more than expected), suspect this same re-render behavior before assuming it's a new bug.

## ⚠ Remove the old inline Custom Code blocks

Before anything else: the live site currently has **leftover inline `<script>`/`<style>` blocks pasted directly into Webflow's Custom Code**, from before this project was consolidated into `sky-ttlr.js`/`sky-ttlr.css`. Specifically, blocks headed:

- `<!-- Sky TTLR — Drag & Drop matching quiz (interact.js) -->` (an older, standalone copy)
- `<!-- Sky TTLR — Episode router: ... -->` (an older, standalone copy)
- A second, redundant `<script src=".../interactjs/dist/interact.min.js">` tag

Add to Webflow Site Settings → Custom Code → **Head**:

```html
<script src="https://cdn.jsdelivr.net/npm/interactjs/dist/interact.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/canvas-confetti@1/dist/confetti.browser.min.js"></script>
<script src="https://cdn.jsdelivr.net/npm/swiper@12/swiper-bundle.min.js"></script>
<link rel="stylesheet" href="https://cdn.jsdelivr.net/npm/swiper@12/swiper-bundle.min.css">
<link rel="stylesheet" href="https://cdn.jsdelivr.net/gh/elisa-sanchez-mb/sky-ttlr@v1.11.0/sky-ttlr.css">
```

`sky-ttlr.css` must load **after** Swiper's own stylesheet (order matters — it neutralizes a couple of Swiper's own rules on `.swiper-button-prev`/`-next`, see the Series swiper description above; if Swiper's CSS loads after `sky-ttlr.css` instead, its rules would win the cascade back and re-break the nav buttons).

Add to Webflow Site Settings → Custom Code → **before `</body>`** (after `webflow.js` and after Memberstack's own script tag):

```html
<script src="https://cdn.jsdelivr.net/gh/elisa-sanchez-mb/sky-ttlr@v1.11.0/sky-ttlr.js"></script>
```

`interact.js`, `canvas-confetti`, and `swiper` are third-party dependencies (drag-drop quiz, the series-end celebration, and the series carousel, respectively) loaded from their own CDNs rather than bundled into `sky-ttlr.js`, so each keeps its own versioning/caching. `interact.js` and `swiper` are optional at runtime — if either fails to load, that one feature no-ops rather than throwing, and everything else is unaffected. `canvas-confetti` is **self-loading**: the Head `<script>` tag above is a nice-to-have (avoids a load delay the first time "Finish Series" is clicked), not a requirement — if it's missing, the script injects it itself on demand, the same self-sufficient pattern the site's own stacked-apps launcher uses for Memberstack. Swiper's own bundled CSS **is** loaded (`swiper-bundle.min.css`, pinned to the same version as its JS) — see the Series swiper description above for what `sky-ttlr.css` overrides on top of it and why.

**To ship an update:** push to `main`, tag the commit (`git tag vX.Y.Z && git push --tags`), then update the `@vX.Y.Z` in both Webflow URLs to match.

**When transferring to `makebuild-code` later:** switch this section back to GitHub Pages (repo Settings → Pages → Deploy from a branch → `main`, `/root`, needs org admin), and update the two Webflow URLs to `https://makebuild-code.github.io/sky-ttlr/sky-ttlr.js` / `.css` — same pattern as `wih1-quiz`. Note that model drops version pinning: Pages always serves whatever's on `main`, so treat `main` as production once that switch happens.

## Required Designer steps

These Custom Attributes have to exist on the live markup for the scripts above to work — none of this is optional:

- **`data-episode-id`** on `.ttlr_episode_cms_item` — bind to the item's **Item ID**, not Slug. Both bookmarks and progress key off this value, so if it's bound to Slug, renaming a slug later orphans that episode's saved data. Currently bound to Slug on the live pages (e.g. `every-connection-counts-3`) — should be rebound to Item ID. Purely a Designer-side change; the script already reads whatever's there generically.
- **`data-series-id`** on `.ttlr_episode_cms_list` (or any ancestor of it — the script walks up with `.closest()`) — bind to the *current* Series item's own Item ID or Slug (this page is that item's own CMS template page). **Present** — confirmed on `<main data-series-id="...">` in the live markup.
- **`data-zone-id`** (static, one per zone: `"1"`–`"4"`) and **`data-correct-zone`** (CMS-bound, per prop) — both already present and correctly assigned by the drag-drop script itself at runtime; nothing to add here.
- **`.ttlr_dragdrop_drop-zone` needs a real height** in Designer — currently an empty div with no set size, which is very likely why zone drops aren't registering.
- **`[bookmark="btn"]`** — a single button placed once on the page (not inside each `.ttlr_episode_cms_item`), containing the bookmark ribbon SVG with an `<svg><path>` inside it. The script reads/writes that `<path>`'s `d` attribute directly to switch between outline and filled, so the SVG markup needs to be the actual `<svg>`/`<path>` element, not a background-image or other substitute.
- **`[data-bookmark-thumbnail]`** inside each `.ttlr_episode_cms_item` — a wrapper containing an `<img>` (the thumbnail) and one element carrying `data-bookmark-number`/`data-bookmark-name`/`data-bookmark-series` as **attribute values** (not that element's own text content, which is separate/unused). `data-bookmark-name` is the episode's own name (e.g. `"Getting it right"`) — combined with the page-level attributes below into `"S1 EP3: Getting it right"` for the bookmark card's episode field. **On `<body>`, page-level** (every episode on a series page shares these): `data-bookmark-month` + `data-bookmark-year` (combined into `"July 2026"` for the month field) and `data-bookmark-series-number` (the `S1` in the composed title). Composed once, at the moment the bookmark button is clicked, into `ttl-bookmarks` — see Bookmarks above. Any one missing just degrades that part of the composed string rather than breaking the others.
- **`.ttlr_cms_month-list` containing exactly one `.ttlr_cms_month-item`** (an `<a>`, with `data-bookmark="thumbnail-wrap"` on its image wrap, `data-bookmark="month"` and `data-bookmark="episode"` on its text fields, and `data-bookmark="btn"` on a remove/bookmark icon inside it) — the template the Bookmarked episodes carousel clones once per bookmark. That single template item is never itself shown; the script removes it and appends one clone per bookmark on every render.
- **`.notes_copy_success`** — searched for anywhere inside the notes component root (it's a *sibling* of `.notes_actions` in the current Designer markup, not nested inside the copy button), with its own `.notes_copy_close` close button wired up automatically if present. Falls back to an auto-created placeholder only if the element is missing entirely.
- **`.ttlr_series-end_success`** — a single element placed once on the page (like the bookmark button and progress bar), hidden by default. The script only adds `.is-active` to reveal it when "Finish Series" is clicked; content/layout is Designer's.
- **`.ttlr_completed_episode_wrap`** — same trigger/pattern as `.ttlr_series-end_success` above (hidden by default, `.is-active` added at the same moment) — a separate element in case the two need different placement/content.
- **`[data-series-element="seconds"]`** — a single element whose text content the script overwrites every second with a count from 30 down to 0, starting the moment "Finish Series" is clicked. At 0, every `[data-series-nav="next-btn"]` on the page gets auto-clicked (see Series navigation, given directly in chat).
- **Series cards need nothing added** — the live markup already has everything: `data-series-id` on `.ttlr_badge` (nested inside `.ttlr_completion_tag-wrap`, itself inside `.ttlr_series_card-wrap`), matching the same slug used as `data-series-id` on that series' own episode-list page. The script writes the "3/5"/"Completed" text into the badge's own inner `<div>` and hides `.ttlr_completion_tag-wrap` entirely if that series hasn't been started yet.
- **`.ttlr_series_card-inner`** (already present, nested in `.ttlr_series_card-progress`) — optional; if present, its `width` is set to match the same completion %. Nothing to add here, just noting it's read.
- **`[data-series-nav="next-wrap"]` / `"prev-wrap"`** (optional) — if the "Up Next"/"Previous" block has an outer wrapper carrying this attribute, it's hidden entirely when there's no next/prev series (e.g. viewing the last series in the list) — otherwise you'd get an empty image + a still-visible-but-disabled button rather than nothing at all. Without this attribute, behavior is unchanged (button just gets `.is-disabled`, text fields go blank).
- **`.ttlr_progress_fill`'s `background` (gradient, etc.) is entirely Designer's** — the script never sets `background` on it (an earlier version tried panning it with `--n`/`--i` custom properties; removed, since the intended look is one continuous gradient revealed proportionally via `clip-path`, not a panned/per-segment color). Keep whatever `background-image` is already declared for it in Designer as-is.

## Memberstack setup

Progress and bookmarks use two **Custom Fields** (Memberstack Dashboard → Settings → Custom Fields — these must be pre-declared, unlike Member JSON), mirroring the exact mechanism the existing app-launcher already uses for its `stacked-apps` field:

- **`ttl-progress`** — JSON-stringified object: `{ episodes: { [episodeId]: { completed, completedAt } }, series: { [seriesId]: { completed, completedAt, completedCount, total } } }` — `completedCount`/`total` are what the home page series card badge reads (see Series cards above); written on every episode completion, not just once a series hits 100%.
- **`ttl-bookmarks`** — JSON-stringified array of bookmark snapshot objects: `{ id, title, month, imgSrc, imgSrcset, href }` (see Bookmarks above). Older data may still be a plain array of id strings — normalized on read into a stub object per entry so nothing breaks, just renders blank until re-bookmarked.

Both fields need to be created in the Memberstack dashboard before the scripts above go live. Read/write happens via `getCurrentMember()` + `updateMember({ customFields: {...} })`.
